How ResQMe works

From a phone's accelerometer to a responder at the scene

ResQMe is an intelligent cyber-physical emergency response system. It detects crashes and falls on the phone, asks if you are okay, and if you do not answer, alerts responders and your contacts with your live location, medical ID and an automatic triage, then sends a drone to look.

Overview

Three layers, one loop

The project frames ResQMe as a loop with three layers: a physical layer that senses, a cyber layer that decides, and an actuation layer that responds. In code that is four deployable parts: an Expo mobile app, a Node.js API with real-time sockets and a drone simulator, a Python AI service, and a responder console, all sharing one PostgreSQL database.

Three rules shaped the design. Detection never needs the network: the phone classifies motion, runs the countdown, and can still dial and text offline. Intelligence degrades instead of failing: every AI call has a timeout and a rule-based fallback. The server is the source of truth: incidents, drones and hazards are saved first and broadcast second.

Sensing the environment

Not everything is sensed on the body. For any location the API reads current conditions from Open-Meteo (cached for ten minutes per area) and turns them into hazards with simple rules. If an area has fewer than three known hazards, a few crime and accident zones are generated from a seeded random generator, so the same street always shows the same demo risks.

Physical to cyber

Detecting a fall or a crash

A phone lying still measures about 1 g. While it falls, that reading drops toward zero; at impact it spikes; and after a real fall, the person (and the phone) lies still. The detector looks for exactly that three-part pattern, using the overall strength of the acceleration so it works however the phone sits in a pocket or bag.

\[ |a| = \sqrt{a_x^2 + a_y^2 + a_z^2} \qquad \text{sampled 50 times a second} \]
  • Impact: the peak reaches the sensitivity threshold: 2.0 g (high), 2.5 g (medium, default) or 3.0 g (low).
  • Free-fall: just before the impact, a run below 0.4 g lasting at least 150 ms. That is a drop of about 11 cm or more.
  • Stillness: in the second after the impact (skipping the first 150 ms of bounce), the readings barely vary:
\[ \sigma = \sqrt{\tfrac{1}{N}\textstyle\sum_k \big(|a_k| - \bar a\big)^2} \;<\; 0.15\ \text{g} \quad \text{over } [\,t_{peak}+150\text{ ms},\ t_{peak}+1150\text{ ms}\,] \]

From a live stream to one decision

On the phone, samples flow into a five-second buffer. When a reading crosses the threshold, the detector waits 1.2 seconds (enough to see the stillness window), then analyses the buffer once. A fall or crash raises an alert and starts a ten-second cooldown so the bounce of one event cannot trigger a second alert. The last five seconds of raw samples travel with the incident, and the server scores them again with its own copy of the algorithm to give responders a confidence value.

Cyber to actuation

Asking first, then escalating

A detection is a guess, so the phone asks. A full-screen "Are you OK?" screen vibrates and counts down. Tapping "I'm OK" cancels; silence sends help. How long it waits depends on who raised the alarm.

TriggerRaised byCountdown
Impactthe detector found a fall or crash30 s
Route deviationoutside the walking corridor for 60 s30 s
Timer expiredthe journey took longer than planned30 s
SOSthe SOS button held for 1.5 s5 s
Manualan explicit report5 s

Someone who pressed SOS already said they need help, so five seconds is just an undo window. An algorithm that guessed gets thirty. After the countdown the phone creates the incident on the server, which then moves from open to acknowledged and dispatched, ending as resolved or cancelled.

If the server cannot be reached, the phone does not wait. It keeps an offline copy of the alert, saves it to storage, and keeps quick dial, SMS and first-aid guidance working while it retries every 10 seconds and whenever the app comes back to the foreground. When a retry succeeds, the offline alert is swapped for the real one without leaving the screen.

After an app restart, the phone restores whatever is still active: a queued offline alert (only for the account that raised it) or a live incident. During an incident it shares its location every 15 seconds if location sharing is allowed, and checks on the assigned drone every 5 seconds in case the live connection drops.

Physical to cyber

Walk with me: the safety corridor

Before walking somewhere, a user taps a route on the map and sets a time limit. The safe area is everything within 150 m of that route. Once a second the app measures how far the user is from the nearest point on it.

At city scale the Earth is flat enough, so each route segment is projected onto a flat grid in metres. The distance to a segment from A to B is the distance to the closest point on it, found by projecting and clamping to the segment's ends:

\[ t^\ast = \operatorname{clamp}\!\left(\frac{(p-a)\cdot(b-a)}{\lVert b-a\rVert^2},\ 0,\ 1\right), \qquad d = \min_{\text{segments}} \big\lVert\, p - (a + t^\ast (b-a)) \,\big\rVert \]

Inside means d of 150 m or less. Staying outside for 60 seconds in a row raises a route deviation alert; getting within 80 m of the destination ends the walk. Separately, running past the time limit raises timer expired. Both go through the same 30 second "Are you OK?" countdown.

Cyber

Real-time alerts

Requests change things; live events announce the change. Every update is saved to the database first and then pushed over Socket.IO to the right people, so a client that reconnects can always reload with one request and then follow the stream.

The live connection is signed in with the same token as normal requests and checked the same way. Every connection joins a private room for its user; responders also join a shared responders room. Signing out of all devices disconnects every live connection at once.

Cyber

Data and security

Ten tables hold the whole system. One choice matters most: an incident keeps a snapshot of the medical ID and contacts from the moment help was requested, so responders see what was true then, even if the user edits their details later.

Encrypted medical IDs

Medical IDs and two-factor secrets are encrypted with AES-256-GCM using a 32-byte server key. Every save uses a fresh random 12-byte IV, and the database stores three values: the IV, a 16-byte authentication tag and the ciphertext. If a single bit is changed, decryption refuses to return anything.

Two-factor sign-in

Users and responders can turn on authenticator-app codes (RFC 6238), implemented with Node's built-in crypto only. The code changes every 30 seconds:

\[ C = \left\lfloor \frac{t}{30\,\text{s}} \right\rfloor, \qquad \text{code} = \operatorname{truncate}\big(\mathrm{HMAC\text{-}SHA1}(K, C)\big) \bmod 10^6 \]

The server accepts the previous, current or next code to allow for clock drift, compares in constant time, and never accepts the same time step twice, so a stolen code cannot be replayed. Eight single-use recovery codes are stored only as keyed hashes.

Sessions, limits and the audit log

Sign-in tokens last 30 days and carry a version number. A request is accepted only if that number matches the user's current version; "sign out of all devices" and password changes bump it, which instantly invalidates every old token and live connection. With two-factor on, the password step only returns a five-minute token that can do nothing except finish sign-in.

Cyber

The AI layer

The AI service is a small FastAPI app with three jobs. Only the crisis chat depends on a language model. Triage is decided by rules (a model may only reword the summary), and motion scoring is plain arithmetic. The rule written into the design: the AI supports people and never replaces emergency services.

Crisis chat

What the prompt asks forShort numbered steps, most urgent first; exactly one follow-up question; for anything life-threatening, the first line says to call the local emergency number; never diagnose; respect allergies in the medical ID; under 120 words.

Triage

Severity is computed by rules so it is predictable and auditable. Impact and SOS start at high; the other triggers at medium. A crash signature or a peak of 8 g sets critical; a high-risk condition such as diabetes, epilepsy, heart disease, asthma or blood thinners raises it one level; and words like "not breathing" or "bleeding" in a note or chat set critical.

Actuation

Drone dispatch

The drones are simulated, and the app says so. Three drones are based at Connaught Place, Saket and Dwarka in Delhi. Once a second the server moves every flying drone, saves it and sends a live update.

Dispatch picks the nearest idle drone (locking the rows so two incidents cannot grab the same one). If none is within 25 km, one is moved to a base 2 to 4 km from the incident. Each second the drone flies 15 m along the shortest path over the Earth's surface:

\[ \text{ETA} = \left\lceil \frac{d - 30\ \text{m}}{15\ \text{m/s}} \right\rceil, \qquad \text{battery drain} = 0.05\%\ \text{per second of flight}, \qquad \text{on scene within } 30\ \text{m} \]
Operations

Deployment

In production ResQMe runs as three Docker containers. Only the API is published; the AI service is reachable only inside the private network, and the database must be healthy before the API starts.

Continuous integration

Every push to main and every pull request runs three test suites side by side, then builds both Docker images. The backend tests run against a real PostgreSQL 16; the AI tests run with the language model switched off; the mobile job runs the logic tests and bundles the Android app.

Honesty

Limits and ethics

An emergency app that overpromises is worse than none. These are the boundaries as built.

  • No silent texts or callsPhones do not let apps send messages or call without the user, so ResQMe opens a pre-filled SMS and relies on the countdown having already alerted responders.
  • Expo Go limitsNotifications while the app is closed and live video calls need a custom build; in Expo Go, hazard alerts are local and detection runs while the app is open.
  • Drones are simulatedThe fleet, bases and flight model demonstrate dispatch and live tracking; they are not connected to real aircraft.
  • AI supports, never replacesEvery serious answer says to call the local emergency number, severity comes from auditable rules, and without an API key everything runs on rules.
  • Detection is a heuristicThe thresholds are based on physics, not trained on a labelled fall dataset. False alarms are expected, which is why the countdown exists.
  • Consent firstLocation is shared only during an emergency and only with permission; the medical ID only with consent; no IMEI tracking.

Run it locally

  1. Install Node 20+, Python 3.11+, PostgreSQL 16 and the Expo Go app (SDK 54).
  2. Create the databases: createdb -U postgres resqme and createdb -U postgres resqme_test.
  3. Copy backend/.env.example and ai-service/.env.example to .env (the OpenRouter key is optional).
  4. Run npm install then npm run setup to install everything and add demo data.
  5. Run npm run dev and scan the QR code with Expo Go. The responder console is at localhost:4100/dashboard.
  6. For production: copy .env.example to .env, then docker compose up -d --build.
